# Knowledge ownership, provenance, and gaps

`knowledge/prototype.json` preserves the supplied source. All 13 original policies plus the original amenities summary are normalized in `demo.json` with `demo_only` status. The two fictional reservation records are separate in `reservations.json`. The user confirmed that the facts are not yet instructor-approved. `approved.json` is intentionally empty.

Every policy has a stable ID, category, topic, answer, source, status, review date, optional expiration, and tags. `knowledge/schema.json` describes the machine-readable format. `approved` records may serve requests. The original `demo_only` records can also be used as visibly labeled, unverified samples when `SAMPLE_KNOWLEDGE=true`, independently of demo mode; set it to false to exclude them. `unverified` draft records are not loaded into retrieval. Approved records take precedence over matching samples. Expired records and conflicting topics are withheld. Exact duplicate IDs are rejected. Add expiration dates to time-sensitive approved records when importing them.

Additional user-supplied CSV/ZIP data is profiled in `source-catalog.json` and represented by six quarantined drafts in `unverified.json`. See [dataset intake](dataset-intake.md) for counts, excluded fields, historical coverage, and limits. These datasets are starting research material, not approved hotel policies or live reservation records.

To submit facts, Wyatt should provide a complete JSON array or CSV with schema fields. CSV tags are separated by `|`; dates use YYYY-MM-DD. Set `approved` only after actual instructor/team review and identify the document/version in `source`. Do not include guests or reservations in this FAQ dataset. Run the importer with `--dry-run` and review added/updated/removed counts. A non-dry run replaces the full approved snapshot atomically and stores a content-hash copy under ignored `knowledge/snapshots/`. Restart the server to load the new snapshot. Commit the reviewed approved file in a PR. Runtime import is intentionally unavailable to guests.

Unknowns: approved hotel address, staff contact channel/phone, actual hours and fees, reservations, service availability, local attractions, transportation schedules, and emergency procedures have not been supplied. The bot must not infer these from the fictional Gainesville location. General contact guidance says to contact a hotel employee directly without inventing a number. Local-area and transportation queries are included in the test set as explicit unknowns.

Coverage is versioned in `tests/scenarios.json`: 34 scenarios include stays, dining, amenities, accessibility, pets, maintenance, housekeeping, billing, distress, transportation, and missing facts. Factual scenarios reference sample source IDs only. Every source requires owner review before being called approved.
